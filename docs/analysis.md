# AI Agent 命理分析指南

技能负责执行顺序，本指南负责分析方法和输出约定；[统一模板](../examples/output.template.json)只规定报告骨架。
引擎提供静态可计算事实，agent依选定古籍论法进行条件性解释；版本分别管理，见第5节。

## 1. 资料与排盘

### 输入解析

从用户原文解析为 `birth/rules/options`。记录字段来源，已经明确的资料不重复要求确认。未决项影响排盘时先补问，不把模板空值直接交给引擎。

|资料|字段与处理|
|---|---|
|性别|birth.sex为male/female，用于传统大运顺逆，不据称谓猜测|
|历法|birth.calendar为solar/lunar；年月日未注明历法时补问|
|生辰|year/month/day/hour/minute；当前引擎要求准确到分钟，不支持缺时或模糊时段，不能用12点占位|
|闰月|农历同名正常月和闰月并存时指定is_leap_month；引擎能查闰月，但不能猜出生记录指哪一个月；公历无须填写|
|地点|longitude或place；先用places查唯一完整路径，同名补问；经度明确时不重复查询|
|时区|timezone或utc_offset_minutes；地点表不含时区，历史记录不能一律假定UTC+8|
|重复钟点|fold=0/1选择夏令时前后分支；不存在的钟点须核实记录，不自动平移|

默认规则：time_basis=apparent（真太阳时）、year_boundary=lichun（立春）、day_boundary=midnight（00点）、late_zi=same_day（晚子时按当日日干起时）。
可选值依次为mean/civil、spring_festival、zi_start、next_day。月柱始终按十二节；太阳时需要经度，缺失不自动退回民用时间。用户指定的规则优先并在结果中展示。

引擎输入可直接用Python `calculate(birth, rules, options)`；CLI使用已补齐的临时输入文件 `bazi chart --input case.json`。
compare用于有必要的规则对照，不以已知经历暗中挑盘。任务临时输入不覆盖模板；name和case_id是报告元数据，不传入birth。报告保存规则见第5节。

### 年份和展开选项

首次默认十步大运及当前立春年；用户明确年份优先。当前立春年由执行时可信时刻与当年立春瞬间比较，立春前取上一年，不使用模型记忆或模板年份。

```python
from datetime import datetime, timezone, timedelta
import sxtwl
now = datetime.now(timezone.utc)
year = now.year
v = next(v for v in sxtwl.getJieQiByYear(year) if v.jqIndex == 3)
d = sxtwl.JD2DD(v.jd)
lichun = (datetime(d.Y, d.M, d.D, tzinfo=timezone(timedelta(hours=8)))
          + timedelta(hours=d.h, minutes=d.m, seconds=d.s))
analysis_year = year if now >= lichun else year - 1
```

报告记录年份选择方式、参考时刻及其来源。只有立春当天的日期而没有时刻时先取得可信时刻或保留未定。指定公历日期按实际所属立春年处理；整段公历年可能需要两个相邻立春年的结果，不能称一个analysis_year覆盖公历全年。

|options|默认与范围|
|---|---|
|luck_count|10，允许1—12步大运|
|analysis_year|引擎默认不展开；agent首报显式选择当前立春年，允许1900—2220|
|include_monthly|false；问题需要月份时开启，必须指定分析年|
|include_auxiliary|false；采用相关辅助论法时开启|
|include_trace|false；时间或规则复核需要时开启|

出生公历年支持1900—2100。输入错误抛BaziError，CLI以状态码2输出结构化错误；未解决的同名闰月、地点、重复时间按错误详情补问，不以相同输入反复重试。
BOUNDARY_SENSITIVE提示要检查实际是否跨交节、换日或时辰；普通整点也可能触发，并不等于排盘错误。

### 排盘资料读取

确认调用成功、schema_version符合第5节的引擎结构版本、input/rules与请求一致，再保留真实结果。没有执行过的调用不得写成已运行。

|分析目的|引擎字段|
|---|---|
|核实时间与规则|input、rules、time、warnings；需要时trace|
|原局、根气与十神|natal四柱及hidden；日主是natal.day，不另造一份日柱|
|月令深浅|season前后十二节、交节时刻、入节时长|
|结构配合|顶层relations，只说明字面关系，不证明合化|
|大运|luck的顺逆、起运年龄、交运时间和各步概览|
|具体年份与月份|analysis.annual、analysis.periods，以及按需展开的analysis.monthly|
|辅助|auxiliary中的纳音、旬空、胎元、命宫、神煞及两种十二长生参照|

## 2. 原局分析

以《子平真诠》的月令格局论法为主线，配合其他古籍；这是项目整理顺序，不是各书共有的唯一次序。
每条关键判断直接记录：结论、实际排盘依据、所用论法、古籍出处、成立条件与未决因素。事实与解释分开，不能只罗列术语。

### 日干与月令

先识别日干，再核对月支、藏干、透干及season前后节。区别月令本气、藏干透出与其他柱透干：例如庚透并不等于辛透，阴阳十神要分别处理。月令格局提供主线，但不能仅看月支就结束全局分析。

记录月令所藏哪些干、哪些有同干透出、是否受其他干支作用；未找到适合论法时保留候选，不随意归入特殊格。入节时长可描述季节深浅，不能伪装成古籍一致认可的分日司令表。

### 力量与根气

分别检查日主与财官杀印食伤比劫，不只评日主一个对象。

- 得令：季节对该五行的条件，不等同字数最多。
- 通根：天干在何柱藏干有同干或同五行支持；本气、余气的权重须解释，不能用藏干排列直接当力量比例。
- 透藏：地支所藏能否由天干表达，位置是否相邻，有无争合或阻隔；合冲存在并不自动消灭藏干。
- 生扶、泄耗、克制：先标作用来源，再考察作用者自身是否有根有力，以及作用链是否受到制约。
- 反证：印透未必足以扶身，财多未必有力，日主有根也未必旺。十二长生仅作所选论法的辅助，明确按日主还是各干自坐。

结论用“哪些条件支持、哪些条件限制”表达；不足时在uncertainties中说明未决条件，不制造强弱百分比。需要比较不同假设时并列条件，不让假设成为已知事实。

### 格局与成败救应

读《子平真诠》用神及成败救应相关篇，明确这里“用神”的月令语境。
先列格局候选所需条件，逐一检查原局配合、日主承受条件、清浊及混杂因素，再问有无损伤、补救是否实际有力。
相同十神组合因月令主线不同，不能只按字面标签互换名称。不要把“财官印俱见”直接当三者皆可用。

从格、化格等特殊判断须独立列必要条件与反证；若同局有显著逆势或支持未尽核对，先保留普通格局解释，不以“看起来偏枯”直接判从。列出天干五合或三会不等于化气成功。

### 寒暖燥湿与气势

以《穷通宝鉴》日干、季节条目作条件性参考，不把每条季节取用当所有命局的固定处方。实际寒暖燥湿要结合全局，节令不是出生地当天气象，引擎也没有测量湿度温度。

气势分析记录可能的生克链、汇聚点与受阻位置，例如某五行能否承接上游并引向下游；区分“字面上有生克路线”与“论法上足以流通”。对于枯燥、寒湿、一气等用语说明判断条件，不能直接变成生活事件。

### 喜忌及论法协调

分别写：格局所用及救应、扶抑需要、调候需要、气势流通需要。若方向一致，说明共同条件；若冲突，列优先考虑的原因、适用范围与未决问题，不把多个“用神”强行合成一个字。
喜忌可能随大运条件变化，不能把暂定五行推广为固定幸运色、配饰、居住方向或投资指令。未充分论证时应保留未定。

## 3. 岁运分析

先固定原局判断的条件，再看大运改变哪些配合，最后加入流年和必要的流月。读关系时合并顶层relations、当年analysis.periods对应段及流月对应段；某层未重复列出的原局关系不是消失。

- 大运概览只含干支和时间，不含完整关系。细论某一步时，可按该步开始时刻所属立春年重新调用，选匹配区间；不能将一个年份推广为整步十年的结论。
- 分清原局—运、原局—年、运—年及多方组合。记录“原局条件→岁运变化→可能影响主题→成立条件/反证”，不从某个冲直接跳到具体事件。
- analysis.periods按交运时刻分段，区间左闭右开；首次起运前luck为null，不自行补小运或前一步大运。
- 流月按节月起止，不以农历初一代替。跨交运月份按对应periods分别解释。
- 大运前后五年等解释法若采用，注明出处与条件，不当作引擎事实。引擎没有给出的关系若由分析者推导，明确标为分析者推导。

## 4. 分项与持续问答

|主题|分析线索与边界|
|---|---|
|性情|结合十神配合及制化，不从日干或单个十神定人格|
|学习|考察印、食伤及整体配合，不见印就断学历、考试名次|
|事业|沿格局、力量与岁运条件解释，不指定唯一行业、职位|
|财务|看财与日主、食伤官印比劫的配合，不以财多断富或以见财断获利|
|婚恋|日支及选定传统论法的对应十神只是线索，见冲不直接断离异；现实关系结构以用户说明为准|
|六亲|宫位、十神与现实背景合看，不把克制关系写成亲属确定遭遇|

每项先说排盘依据，再说解释及不足。默认不增加疾病、寿命、灾祸栏目，也不输出诊断、确定日期或具体投资指令。

|追问类型|处理|
|---|---|
|解释已有结论|复用有效资料，说明依据和推理桥梁，不重排整份报告|
|新年份或月份|按需调用相应analysis_year/include_monthly，保留仍有效的原局判断|
|修改出生资料或规则|birth_revision递增，重新排盘，指出改变的字段并重建受影响结论，不能沿用旧日主十神|
|新增现实经历|标为用户提供的背景，可检验解释条件，但不倒改规则迎合经历|
|缺少必要信息|自然语言补问，结构化澄清时填写questions，不索取无关资料|

同资料、规则、年份且展开选项足够时复用结果。追问对象不明确时补问，明确时直接读取对应资料。跨会话读取保存报告中的规范化生辰、规则与修订号；没有可读报告或有效上下文时不假装记得旧分析。追问与报告更新的边界统一见第5节。

## 5. 统一输出约定

### 版本与适用对象

|版本|当前值/来源|含义|
|---|---|---|
|项目版本|0.2.0，定义于pyproject.toml|Python安装包版本，对应引擎结果的engine_version|
|引擎结构版本|schema_version为2.0|calculate/compare返回的排盘结果结构|
|报告模板版本|template_version为2.1，见[输出骨架](../examples/output.template.json)|agent完整报告结构，chart中嵌入引擎结果|
|报告文件序号|report-001.json起递增|同一资料的保存版本，不是结构版本|
|资料修订号|context.birth_revision从1开始|同一资料生辰或规则的修订次数，不随分析年份变化|

这些版本独立管理，不要求数值一致。模板是空骨架，不是引擎输入或已完成报告。

### 字段与表达
完整报告文件是一个JSON对象，不附Markdown围栏或JSON外解释，顶层字段保持完整；首次报告填写input/chart/natal/fortune/domains。澄清可先自然语言补问；使用结构化澄清时report_type为clarification，只填相关资料和questions，其余为null或空数组，不保存为完整报告。追问不使用本模板，直接自然语言回答；保存成功通知也用普通对话，不受报告JSON约束。

|字段|填写方式|
|---|---|
|name|用户提供姓名时，去除首尾空白后填入此字段；未提供或为空时填“用户1”。仅作显示，不是唯一标识|
|case_id|首次建立资料生成UUID，格式见下文；同一资料复用时保持稳定|
|report_type|initial或clarification；新保存的完整报告仍为initial，不代表只能生成一次|
|status|complete、partial或needs_input；流程完成不代表判断必然准确|
|context|生辰修订号、实际rules、analysis_year、year_selection及未决项；year_selection记录方式、参考时刻和来源|
|input|原文、normalized_request、字段来源、未决项；补齐前不运行|
|chart|直接填真实引擎结果，不能按模板手造。多年份调用填结果数组，即单个结果对象或对象数组；不重复放入分析正文|
|natal|日主、月令、力量、格局、寒暖燥湿、气势、喜忌，各组为判断记录数组|
|fortune|overview为各步阶段解释；years按年份和实际交运区间解释，保留对应start/end|
|domains|六个默认主题各为判断记录数组；不足就说明未定，不填通用吉凶套话|
|questions|确有必要的补问；无则空数组|

判断记录统一采用模板natal.day_master中展示的结构：conclusion、basis、method、sources、conditions、uncertainties。
basis各项写field和observation，例如field为natal.day.ganzhi；不使用JSON Pointer或全局判断编号。
多盘时field补明年份/规则分支，观察必须对应实际结果；来源直接随判断附书名、版本、篇章、核验状态、page和quote，未核实页码或引文填null。项目归纳用verification=synthesis，不能冒充古籍原句。
conditions可以记录反证、救应和适用范围；条件不足时在uncertainties写清，允许结论暂不确定。示例记录只是字段骨架，应复制结构后填真实内容，不把空对象当作完成分析。

### 姓名、资料识别与保存

- 首次建档用 `str(uuid.uuid4())` 生成小写标准UUID作为case_id；已有资料保留case_id。不用姓名或生辰散列代替唯一编号，也不因同名自动合并。
- 同一会话对象明确时直接复用。按姓名查找时，若只有唯一匹配且上下文一致可复用；多个匹配或身份不清时补问，可用case_id定位。遇同名但不同生辰且意图不明时先问是更正同一人还是新增另一人。
- 首次完整报告默认保存到项目根下 `outputs/<case_id>/report-001.json`。需要保存时才创建目录；该目录已由Git忽略。成功写入并检查JSON后，简短告知姓名、case_id及可点击文件链接；保存失败如实说明，不宣称已保存。
- 路径只使用校验后的标准UUID和固定格式版本名，不将用户姓名或任意输入拼接为路径。已有case_id先校验格式并定位本地报告；查不到时说明，不自动伪造旧档。
- 用户明确要求更新时，读取该case目录中report-NNN.json的最大数字版本，另存下一个版本，编号至少三位；已有文件不覆盖，若候选名已存在继续取下一空闲编号。首次保存也先检查目录，不能把“001”作为无条件覆盖位置。
- 更新分析年或解释只增加报告文件序号；明确更正同一人的生辰或规则时保留case_id，增加birth_revision、重新排盘并重建受影响分析。
- 追问中的生辰更正、新年份或新计算结果先在会话中使用，不自动修改已有报告；明确要求更新后再保存新版。恢复旧报告时注意当前birth_revision与规则，不把旧结论混入修订后的资料。
- 跨会话以用户提供的case_id/报告或明确可识别的姓名读取现有档案；默认选数字版本最大的已完成完整报告。保留旧版以便对照，但不能把版本大小当作预测可信度。

完成前核对：JSON可解析、name默认值及case_id正确、字段与真实排盘一致、交运段正确、来源状态真实、旧结论已更新、保存路径和版本未覆盖。完整报告不包含followup字段或追问日志。不再维护独立报告Schema、来源注册表或依赖图。

### 版本与篇章

|书籍|本地选用版本与用途|
|---|---|
|渊海子平|1634年余氏善成堂明刊本；基础规则与格局查考|

### 现代约定与适用范围

- 公农历采用现代历法回推，不是复原历史授时历。海外农历先转公历日期标签，再配当地钟表时间，时区另指定。
- sxtwl节气JD在适配层按UTC+8表达解读后转UTC；年月交界比较同一绝对时刻，不能只修正出生钟点而移动节气。
- 默认立春换年、十二节换月；春节换年只是可选对照，月干仍从立春年干推算。00点换日的依据不单独证明晚子时必须借次日日干，两项分别配置。
- 真太阳时=UTC钟点+经度×4分钟+均时差；正均时差表示视太阳时快于平太阳时。公式与时区是现代计算约定，不伪称古籍原载。参照[太阳计算说明](https://gml.noaa.gov/grad/solcalc/calcdetails.html)。
- 起运三日折一年以实际UTC间隔折算，象征年360日、月30日，再按公历加算交运日期；后一步是工程落实约定，月末截至当月末日。
- 时区用IANA数据；引擎记录依赖版本。显式UTC偏移可用于历史争议。地点表是用户已有近似坐标，来源、坐标系及再分发许可未确认。
- 秒数是计算分辨率，不等于出生记录或天文绝对精度，未完成独立天文数据全范围精度认证。
- 十二长生区分日主查各支与各干自坐；旬空按reference所指柱，藏干顺序不代表力量比例。神煞采用表不穷尽古籍异说，未命中不等于另一论法也不存在。
- 历法正确、古籍有载与预测准确是不同问题。报告是传统体系的条件性解释，不输出精确概率、吉凶分数或必然事件清单。
